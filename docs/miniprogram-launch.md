# 小程序上线手册（沪上双周活动）

配套 README 第「微信小程序」章节。本文只讲**怎么从 0 走到线上**，以及上线前必须补的缺口。

## 0. 链路评估结论

链路设计成立，不是空架子：

- `cloudrun/server.js` 本地直连 Supabase 实测通过，`/api/events` 返回真实数据（评估当天 157 条，补图过滤后复测 199 条，随每两日采集变动）；
- 响应字段与 Web 端 `src/app/api/events/route.js` 完全一致（11 个公开字段，无内部字段泄漏）；
- `week / category / search` 三个参数与参数校验全部生效（非法分类返回 400）；
- `src/lib/events.js`、`src/lib/dedupe.js` 是零外部依赖的纯函数，`Dockerfile` 只 COPY 这两个文件即可，逻辑复用成立；
- `wx.cloud.callContainer` 走微信内网，**不需要服务器域名、不需要 ICP 备案**，个人主体可用。

采集层完全不用动：GitHub Actions 每两日写 Supabase，小程序与 Web 端读同一份数据。

## 2. 非阻塞但建议修

- ~~封面图相对路径~~ **已修**：`cloudrun/server.js` 的 `toPublicEvent()` 现在会把非 http(s) 的 `image_url` 置为 `null`（当前 199 条里 126 条无封面，73 条正常）。小程序 `<image wx:if>` 直接不渲染，走无图样式，不会有裂图。这是与 Web 端 DTO 的**有意差异**——Web 端把相对路径交给 `src/lib/image-url.js` 在前端过滤。
- **报名直达未启用**：`utils/registration.js` 的 `REGISTRY` 三个 appId 都是空的，当前所有报名都走「复制链接」降级。填 appId 后记得同步改 `app.json`（见上表第 4 项）。
- **⚠️ 小程序名称（比原先估计的严得多，2026-10-06 据腾讯客服《小程序名称、简称设置规范》修正）**：
  原先这里写「`沪上双周活动` 含地名，个人主体**可能被要求说明**」——**这个判断是错的，太乐观了**。
  官方口径是：**名称含地名，必须提交「政府部门出具的授权书」并加盖公章**
  （要写明授权主体、授权使用昵称范围、授权期限，且授权方须提供官网可核实的联系方式）。
  **个人主体拿不到政府授权书，所以只要名字里有「上海」「沪」基本必挂**。改名后的候选见 §2 候选名。
  另外两条容易踩的：① **小程序名称在微信公众平台是全平台唯一的**，且与公众号同一个命名池
  （所以「活动雷达」「城市活动」这类通用词几乎必然被占）；② 不得用「电话 / 邮件 / 日历」这类
  **广义归纳类、普遍且不具识别性**的词**单独**做名字，必须是**两个词以上的组合**。
  长度：**4–30 个字符，1 个汉字 = 2 个字符**（即 2–15 个汉字）。
  ⚠️ **本条只约束「小程序名称」这个账号名，不约束 App 内的界面文字** ——
  `app.json` 的 `navigationBarTitleText: "上海城市生活雷达"` 属于界面文案，**可以继续用「上海」**，
  不必跟着改。两件事分开看。
- **⚠️ 实例副本数最小值建议设为 1（冷启动，2026-10-04 实测踩到）**：云托管默认实例缩容到 0，隔一段时间不访问后  
  第一个请求要等实例拉起，超过 `callContainer` 的 **15s 上限**就报 **`102002`（请求超时）**，用户看到的就是一屏报错。  
  位置：云托管控制台 → **服务设置 → 实例副本数 → 最小值设为 1**，让服务常驻。  
  代价：实例不再缩容到 0，会持续消耗资源与费用，而**第 1 个环境只有 3 个月免费额度**，请自行权衡。  
  代码侧已加兜底（`utils/api.js` 检测到 `102002` 会隔 1.5s 自动重试一次），但那只覆盖「重试就好」的情况，**根治仍在控制台**。
- **订阅消息**：个人主体只能用一次性订阅，活动开始前提醒可以后续再接。

## 3. 注册小程序，拿 AppID

1. 打开 <https://mp.weixin.qq.com> → 右上角 **立即注册** → 选 **小程序**。
2. 填一个**从未注册过公众平台**的邮箱 → 去邮箱点激活链接。
3. 主体类型选 **个人** → 填身份证姓名 + 号码 → 管理员微信扫码（管理员本人需微信实名）。
4. 填小程序名称、简介 → 提交，注册完成。**名称候选见下（这一栏最容易反复被拒）。**
5. 进入后台 → **开发管理 → 开发设置** → 复制 **AppID（小程序 ID）**，形如 `wx` 开头 18 位。这一步的产物就是它。
6. （强烈建议）**设置 → 微信认证 → 个人认证，30 元**。个人主体不认证也能跑，但云托管环境创建、审核通过率都会更顺。

### 4a. 小程序名称候选（2026-10-06 定）

取名必须同时躲开四个雷（判据见 §1 的「小程序名称」条）：
**不含地名**（「上海/沪」→ 要政府授权书，个人主体不可能）· **不撞全平台唯一名**（通用词基本被占）·
**两个词以上组合**（不能只用「活动」「日历」这类无识别性的词）· **4–30 字符（1 汉字 = 2 字符）**。

设计思路：**时间维度 + 内容维度 + 一个识别性词**。产品实际口径就是「从今天起 +14 天」，所以「双周 / 两周」既贴合功能又是天然的区分词。

| 候选 | 汉字 | 字符数 | 可截取的简称 | 说明 |
| --- | --- | --- | --- | --- |
| **双周活动雷达** ★首选 | 6 | 12 | `双周活动`（8 字符） | 时间+内容+意象三词组合；不含地名、不含资质词；「双周」正好等于产品的 14 天窗口 |
| 两周活动雷达 | 6 | 12 | `两周活动` | 同上，换一个时间词，可用于撞名时平替 |
| 双周文艺雷达 | 6 | 12 | `双周文艺` | 偏文艺向；但如果以后大量收 AI 聚会类活动，「文艺」就不准了 |
| 城市活动雷达 | 6 | 12 | `城市活动` | 舍掉时间维度换通用性，**撞名概率最高**，放后面试 |
| 双周活动速览 | 6 | 12 | `双周速览` | 「雷达」被占或被认为不妥时的退路 |

⚠️ 提交前先做**零成本预检**：在微信「**搜一搜**」里搜候选名。若能搜到同名的小程序或**公众号**，
必然被拒——因为小程序名称在公众平台是**全平台唯一**的，且与公众号共用同一个命名池。
这一步不消耗任何改名次数。

⚠️ 如果几个候选都被拒，且提示**不是**「已被占用」而是「涉及地域名称 / 需提供授权」，
说明被判定了别的东西（例如「城市」在某些类目下也可能被要求说明），换更"纯组合"的名字再试。

1. **必须与名称、实际功能一致**，**不得含与功能无关的搜索热词**。上面每一条都能在代码里对上：

3. 每个月 5 次修改机会。
4. 💡 **名称里不能带的「上海」，正好放这里带**——简介不受地名字限制，而且这是用户搜「上海 活动」
   能命中你的地方。这也是为什么主推版保留了「上海」二字。

（与 §4a 的名称规范同站，属官方口径）。**这些次数是稀缺资源，动手前先看这张表。**

| 项目 | 修改次数 | 规范要点 | 入口 |
| --- | --- | --- | --- |

| 小程序简称 | 发布前 2 次 / 发布后 **2 次每自然年** | 从名称**按顺序截取**，4–10 字符；简称不唯一（可重名） | 设置 → 基本信息 |
| **小程序头像（logo）** | **每个自然年 5 次**，次年 1/1 自动重置 | 格式 **bmp / jpeg / jpg / gif**；**≤ 2 MB**；不得涉及政治敏感与色情 | 设置 → 基本信息 |
| 小程序介绍 | **每月 5 次** | 4–120 字符（1 汉字 = 2 字符，实测约 60 汉字，见 §4b） | 设置 → 基本信息 |

关于头像的几条硬事实（来自微信开放社区官方答复）：
- **用尽后只能等下一个自然年 1 月 1 日**自动重置，**没有人工申请额度这回事**。
- ⚠️ **重新做微信认证不能重置头像次数**——该限制独立于认证状态，别为了刷次数去花钱认证
  （社区里就有人「白花钱重新认证了」）。
- 唯一例外：**头像因侵权投诉被系统清空**的，会自动返还 **1 次**额外机会。
- 想查本年度已经用了几次：**小程序后台 → 设置 → 操作日志**。社区里有人「觉得没换过、次数却没了」，
  就是靠这里对账的。
- ⚠️ **因此别拿正式上传去试样式。** 先在本地把图定稿（见下），再消耗次数。

头像图片本地预处理（够用的一张就够）：
```bash
# 先看清现状：尺寸、比例、体积
sips -g pixelWidth -g pixelHeight /path/to/logo.png

# 裁成 1:1 并拉到 1024×1024（>100×100 即可，1024 上采样到各端都清楚）
sips -c 1024 1024 -s format jpeg -s formatOptions 85 /path/to/logo.png --out logo.jpg
```
建议：**1:1 正方形**（非正方形会被拉伸/裁切变形）、**≥ 100×100**、控制在 **2 MB 以内**。
官方原文列的格式是 `bmp / jpeg / jpg / gif`，**没写 png**（实际一般也能传），
所以**顺手备一张 JPG**，万一 PNG 被拒不用再消耗一次机会。

### 4d. 小程序备案（ICP）：备注与服务内容怎么填

官方口径：微信《小程序备案常见问答》
<https://developers.weixin.qq.com/minigame/product/record/company_representative.html>。
**总原则：备案小程序名称 / 小程序服务内容 / 小程序备注 / 主体名称，这四要素必须相互关联，
出现明显相悖即驳回。**

#### 备注（必填，20–200）— 主推 93 字符，直接复制

```
本小程序为个人非经营性信息查询工具，汇总上海市公开发布的展览、演出、讲座等文化活动的时间、场馆及公开链接，供免费查询。不涉及交易、购票、付费等经营性功能，不涉及新闻时政，无用户发布内容。
```

⚠️ **字数口径的坑（2026-10-06 实测踩到，务必先看）**：这一栏写的是「20-200 **字**」，
**但平台实际是按字符总数卡的，不是按汉字数**——所以预算是 **200 个字符**，中文标点也各占 1 个。
第一版我按汉字数写，181 个汉字看着很安全，**实际字符总数 210，超 10 个，被驳回**。
上面这版 **93 个字符**，即使按最严的「中文算 2 个字符」口径也只有 186，**两种口径都安全**。

自查办法：把文本粘进输入框，光标拉到末尾看计数器显示多少——显示 ~93 就是按字符算，那还有空间，
可以换用下面这个**更全版（113 字符）**，把「音视频、直播、需前置审批业务」几个排除项补回来：
```
本小程序为个人非经营性信息查询工具，汇总上海市公开发布的展览、演出、讲座等文化活动的时间、场馆及主办方公开链接，供用户免费查询。不涉及交易、购票、付费等经营性功能，不涉及新闻时政、音视频、直播及需前置审批业务，无用户发布内容。
```

写备注的 6 条：
1. 开头用官方建议句式「本小程序为……主要内容为……」，让审核一眼看懂业务边界。
2. **写业务，不写技术**——不要出现「React / 云托管 / 自动采集 / 爬虫」这类词，
   也不要把「无代码/AI 生成」写进去（判为信息不完整）。
3. **主动写明"不涉及什么"**：这是减少人工核查、避免被要求补前置审批材料最有效的一招。
4. 备注里的排除项**必须与「服务内容」勾选一致**（见下，本项目踩了这个坑）。
5. **按"字符总数"核算，不是按汉字数**（见上面的坑）。数字符：`len(文本)`。
6. 「无用户发布内容」这句别省——它同时排掉了 UGC 内容安全和社交类合规的追问。

#### 服务内容（管局的行业分类，与平台的"服务类目"不是同一套）

- ⚠️ **个人主体不得勾选经营性质、企业/单位性质、需主管部门审批的内容**
  （官方原文举例：个人主体不可选「批发和零售业—零售批发」）。
- ⚠️ **「旅游服务」建议去掉。** 本项目没有任何旅游、景区、票务、行程功能，
  而备注里明确写了「不涉及旅游」——**勾着"旅游服务"、备注写着"不涉及旅游"，正是典型的四要素相悖。**
  建议只保留「生活服务 / 其他」，或在下拉里找更贴切的「信息查询」类二级项。

#### 前置审批项

**不涉及也必须选/填「以上都不涉及」**（官方 FAQ 原话：如不涉及前置审批项，也需要填写"以上都不涉及"）。

⚠️ **名称里的前置审批关键词会被平台预筛**，官方关键词表包含
「演出剧目 / 演出节目 / 组织文化艺术交流活动 / 艺术品 / 网络文化经营 / 新闻 / 新闻发布」等。
**「SH城市活动雷达」不含这些词，安全。** 但备注里也**不要**写「剧目 / 文化艺术交流 / 网络文化经营」，
改用「文化活动信息汇总」这类中性表述，避免被人工判定为需要《网络文化经营许可证》。上面这套文案已避开。

#### 个人主体备案的硬提醒（官方 FAQ）

- 个人主体备案小程序**数量上限 5 个**。

## 9.1 数据保留与清理（2026-10-03 重构）

**展示口径与存储口径是两件事，不要混。**

|        | 规则                                                                                                         | 代码位置                                                                                        |
| ------ | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 展示（读）  | 只出**未结束**的活动：`(coalesce(end_time, start_time) at time zone 'Asia/Shanghai')::date >= 今天的上海日期`，上界仍为今天 +14 天 | `src/lib/repository.js` 的 `buildEventWindowWhereSql`、`cloudrun/server.js` 的同名函数（**两处必须一致**） |
| 存储（清理） | 删除**结束时间**早于 7 天前的行                                                                                        | `src/lib/repository.js` 的 `buildCleanupSql`，`EVENT_RETENTION_DAYS = 7`                      |


**两个必须知道的坑：**

1. **清理的判定基准必须是 `coalesce(end_time, start_time)`，不是 `start_time`。**  
   长期展览（如 7 月开幕、次年才结束）的 `start_time` 很早，按 `start_time` 会被误删——但它仍在展出，是有效内容。实测：本库有 143 条"开始很早但还没结束"的活动，按旧写法会全部被误删。
2. **定时任务的 cron 字段顺序是「分 时 日 月 周」。**  
   `cleanup.yml` 曾写成 `0 2 1 */2 *`，那个 `*/2` 落在**月**字段 → 等价于"奇数月 1 号"，一年只跑 6 次，导致过期数据堆了三个月。正确写法见 `collect.yml` 的 `0 1 */2 * *`（每 2 天）。现已改为每天 `0 3 * * *`。

另外：`raw_event_ids` / `sources` 这类 jsonb 大字段在**本地脚本里用 `select *` 拉取时可能让进程被系统杀掉**（实测 exit 137），备份脚本请显式列字段。

## 9.2 长期活动的 end_time 补齐与「发布/读窗口口径一致」铁律（2026-10-03）

### 问题一：长期活动没有 end_time，会同时坏掉展示和读窗口

展览、驻场演出的源页面经常只给开始日期。`end_time is null` 时，  
`coalesce(end_time, start_time)` 会落到 `start_time` 上，于是这档活动被当成「开幕当天就结束」——  
读窗口不显示它，清理任务也会在开幕 7 天后把它删掉。

**解法**：`src/lib/event-duration.js` 提供 `inferEventEndTime(event)`，  
在发布收口 `filterPublishableEvents`（`src/lib/events.js`）里对每条事件生效：

| 判定                                                             | 结果                  |
| -------------------------------------------------------------- | ------------------- |
| 源已给结束时间且晚于开始                                                   | 原样保留（一手数据优先）        |
| 命中单场信号（`音乐会/独奏/交响/协奏曲/室内乐/开幕/导览/讲座/沙龙/工作坊/放映…`）                | **保持 null**         |
| 类别是 `展览`，或命中长档期信号（`音乐剧/话剧/舞台剧/歌剧/沉浸式/驻场/驻演/公演/剧场/演出季/艺术节/市集…`） | `start_time + 90 天` |

**为什么必须「选择性」补齐**：给一场钢琴独奏编 3 个月结束时间，会让它在首页挂三个月并挤掉真正的活动——  
那是把错误放大，不是修掉。单场信号优先级高于长档期信号。

存量行用 `node scripts/backfill-end-time.mjs`（默认干跑，`--apply` 才写，写入前自动落 JSON 备份到  
`.workbuddy/backups/`）。幂等：只处理 `end_time is null` 的行。  
2026-10-03 首次执行：370 行里 93 行 `end_time is null`，判定补 7 行、留 86 行，读窗口召回 276 → 277。

### 问题二：发布口径必须与读窗口口径完全一致

`publishEvents` → `replaceWeekEvents` 的实现&#x662F;**「先按读窗口 `delete from events`，再插回本次采集集」**。  
所以只要发布口径（`isInDateRange`）比读窗口口径（`buildEventWindowWhereSql`）**窄**，  
落在两者差集里的行就会被**删掉且永远不再写回**。

旧实现里 `isInDateRange` 带着「展览回看 60 天 / 高校讲座回看 30 天」的分类分支，  
而读窗口没有这个上界收缩 —— 实测：**读窗口 277 行里有 147 行**会被静默吃掉，  
包括 `世界树之巅：美洲古代文明大展`（7.9 开幕）、`塑我此生：贾科梅蒂艺术大展`（7.17 开幕）等仍在展的长期展览。

现在两处统一为同一条判据：

```
start_time <= endDate 且 coalesce(end_time, start_time) >= startDate
```

`test/repository.test.js` 里有一条回归护栏专门钉这个不变量  
（`publish predicate matches the read window so long-running events are never dropped`），**不要删**。

## 9.3 首页：按天分组的日程表（2026-10-04 改版）

首页不再是「推荐 / 最新」排序的卡片流，改成和 Web 同构的**日程表**：  
封面 → 搜索 → 「正在进行」海报栏 → 吸顶的类目 Tab + 日期条 → 按天分组的列表。  
原来的 `utils/sort.js`（评分排序）和 `components/event-card` 已删除。

分桶逻辑在 `miniprogram/utils/agenda.js`，是 Web 端 `src/lib/agenda.js` 的 CommonJS 移植：  
一条活动占它的整个日期区间，在区间内每一天都算数，只是呈现不同——

| kind    | 含义           | 时间栏显示                               |
| ------- | ------------ | ----------------------------------- |
| `start` | 当天开始         | 钟点（跨天的在标题下写「10.10 — 10.17 · 共 8 天」） |
| `last`  | 当天是最后一天      | 「末日」                                |
| `run`   | 展期中（已开始、未结束） | 「展期」+「至 10.11 · 还剩 3 天」             |

展期中的活动常年有几十场，不能每天全部平铺：每天至少露出 3 行（Web 是 5 行），  
当天开始 / 结束的不够就用展期中的补，**3 天内结束的优先，其余按天轮换**；  
剩下的收进「展期中 · 另有 N 场今天也能去」，点开才 `setData`。

⚠️ 分桶 / 露出规则改动必须**同步改 `src/lib/agenda.js`**（那边有单元测试 `test/agenda.test.js`）。

首页的**类目切换在本地重算**（接口一次返回 14 天全量），只有搜索走服务端。  
`setData` 里只放渲染用的精简字段，完整事件对象留在 `this.pool` 按下标取，避免数据包过大。

## 9.4 日期区间展示（2026-10-03）

`miniprogram/utils/format.js` 提供两个格式化函数，分工不同：

| 函数                | 用途                                                    | 跨月长期展的输出                     |
| ----------------- | ----------------------------------------------------- | ---------------------------- |
| `eventRangeShort` | 紧凑区间（2026-10-04 改版后列表行改用 `agenda.rangeText`，此函数暂无调用方） | `9.24–10.30`                 |
| `eventPeriod`     | 详情页的单日活动（跨天活动改用 `agenda` 拼「区间 + 共 N 天」）               | `9月24日 周四 10:00 至 10月30日 周五` |

两者在**跨日时都不带结束钟点**——跨的是"档期"，结束时刻是当天闭馆时间，没有信息量。  
同一天的活动仍然保留钟点（`10.6 19:30–21:30`）。

卡片角标 `eventBadge`：今天/明天/后天优先；已开幕但未结束的长期活动&#x6807;**「进行中」**  
（这类活动的 `start_time` 在很久以前，`relativeLabel` 返回空，不加这层用户会以为它没有时间信息）。

## 9.5 视觉语言：「素白」杂志编辑风（2026-10-04 改版）

两端共用一套 token，真源是 `src/app/styles.css` 顶部的 `:root`，小程序在 `miniprogram/app.wxss` 的 `page` 里同名同值：

| token                 | 浅色                    | 深色                    | 用途                |
| --------------------- | --------------------- | --------------------- | ----------------- |
| `--paper`             | `#fbfaf7`             | `#201f1d`             | 页面底色（纯色，带一丝暖）     |
| `--paper-2`           | `#f0eeea`             | `#2e2c2a`             | 搜索框、图片占位          |
| `--ink`               | `#191817`             | `#efede8`             | 正文、粗分隔线、主按钮底      |
| `--ink-2` / `--ink-3` | `#5f5d59` / `#918e89` | `#aba8a2` / `#77746f` | 次级 / 弱文字          |
| `--hair`              | 墨色 14%                | 墨色 16%                | 细分隔线              |
| `--accent`            | `#c4472a`             | `#f08a5d`             | 唯一强调色（取自封面插画的珊瑚橙） |

- **没有卡片、玻璃、模糊、圆角、阴影**。层次只靠字号、字重和线：粗线分大段，细线分行。
- **标题和日期数字用系统宋体**（`.serif`）。iOS 有 Songti SC；没有宋体的 Android 会回落到黑体，版式不受影响。  
  不加载网络字体：Web 的 CSP 是 `style-src 'self'`，小程序加载中文字体包又太大。
- **深浅色跟随系统**，两端都不提供手动切换。小程序靠 `app.json` 的 `darkmode` + `theme.json`，  
  `theme.json` 的导航栏 / tabBar 颜色要和 `--paper` 保持一致。
- **强调色只用在**：今天的日期、类目字样、跨天区间、「末日 / 展期」、已收藏。不要拿它当大面积底色。
- **没有图的活动只显示文字**，列表行不放灰色占位块；海报栏和详情头图的槽位底下垫类目字样。

首页是自定义导航（`navigationStyle: custom`）：第一屏是出血的插画封面（`assets/cover.jpg`，  
由 `public/images/shanghai-radar-cover.jpg` 缩到 1000px 宽得到），下滑越过封面后才显示实色标题栏。  
标题栏高度按胶囊按钮位置算（`measureNav`），吸顶筛选条的 `top` 跟着它走。

其余：

| 项   | 做法                                                                                       |
| --- | ---------------------------------------------------------------------------------------- |
| 列表行 | `components/event-row`：左时间、中标题 + 场馆、右 128rpx 方形缩略图。纯展示组件，点击由使用方 `bindtap`                |
| 加载态 | 骨架屏，结构与真实列表行一致                                                                           |
| 详情页 | 出血头图 → 强调色类目 → 宋体大标题 → 粗线信息表；底部固定「收藏 / 报名」操作栏                                            |
