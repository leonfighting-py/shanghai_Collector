# 小程序上线手册（沪上双周活动）

配套 README 第「微信小程序」章节。本文只讲**怎么从 0 走到线上**，以及上线前必须补的缺口。

## 0. 链路评估结论

链路设计成立，不是空架子：

- `cloudrun/server.js` 本地直连 Supabase 实测通过，`/api/events` 返回真实数据（评估当天 157 条，补图过滤后复测 199 条，随每两日采集变动）；
- 响应字段与 Web 端 `src/app/api/events/route.js` 完全一致（11 个公开字段，无内部字段泄漏）；
- `week / category / search` 三个参数与参数校验全部生效（非法分类返回 400）；
- `src/lib/events.js`、`src/lib/dedupe.js` 是零外部依赖的纯函数，`Dockerfile` 只 COPY 这两个文件即可，逻辑复用成立；
- `wx.cloud.callContainer` 走微信内网，**不需要服务器域名、不需要 ICP 备案**，个人主体可用。

采集层完全不用动：GitHub Actions 每两日写 Supabase，小程序与 Web 端读同一份数据。

## 3. 注册小程序，拿 AppID

1. 打开 <https://mp.weixin.qq.com> → 右上角 **立即注册** → 选 **小程序**。
2. 填一个**从未注册过公众平台**的邮箱 → 去邮箱点激活链接。
3. 主体类型选 **个人** → 填身份证姓名 + 号码 → 管理员微信扫码（管理员本人需微信实名）。
4. 填小程序名称、简介 → 提交，注册完成。
5. 进入后台 → **开发管理 → 开发设置** → 复制 **AppID（小程序 ID）**，形如 `wx` 开头 18 位。这一步的产物就是它。
6. （强烈建议）**设置 → 微信认证 → 个人认证，30 元**。个人主体不认证也能跑，但云托管环境创建、审核通过率都会更顺。

## 4. 开通微信云托管，创建环境

1. 打开 <https://cloud.weixin.qq.com/cloudrun>，微信扫码登录（用管理员微信）。
2. 首次进入会让你选「小程序 / 公众号」——**选刚注册的那个小程序**，系统随之创建第一个环境。
3. 付费模式必须是 **按量付费**（云托管只支持按量环境；预付费环境需先切换）。
4. 复制 **环境 ID**（形如 `prod-8g0xxxxxxxxx`）。位置在控制台**右上角的「环境」下拉**里点开就能看到——注意云托管控制台**没有**「环境信息」板块，小程序后台（mp.weixin.qq.com）里也**看不到**云托管，那是两套独立控制台。这就是 `CLOUD_ENV`。
5. 注意：云托管环境和「云开发环境」是两套体系，**只能在云托管控制台看到**，微信开发者工具的云开发控制台里找不到它。
6. **首次进入如果停在「免费快速部署 / 选择模板」页**：随便选 **Express.js** 走完即可——这一步的唯一目的是把环境创建出来（本项目本身就是 Express，选它后续对照最直观）。但**不要把这个示例服务当正式服务**，环境建好后回「服务管理」另建 `events-api`，示例服务可以直接删掉。

关联关系：环境是按所选小程序主体创建的，因此**天然与该 AppID 关联**，`callContainer` 默认只能访问本小程序已关联的环境。跨主体共享要另走「资源复用」，本项目不需要。

## 5. 部署 events-api 服务

1. 云托管控制台 → **服务管理 → 新建服务**，服务名填 **`events-api`**（必须与 `config.js` 里的 `SERVICE` 一致，写错就是 404）。
2. 代码来源选 **绑定 GitHub 仓库** → 仓库 `leonfighting-py/shanghai_Collector` → 分支 `main` → 端口 `80`。
   - 云托管**只在仓库根目录查找 Dockerfile**，仓库根已放了一份（与 `cloudrun/Dockerfile` 内容一致），所以直接点发布即可
   - 构建目录保持默认（仓库根），**不要填 `cloudrun`**——Dockerfile 里要 `COPY src/lib/*`，改成子目录会找不到
   - 想用「指定 Dockerfile 路径」（新建版本 → 高级设置）也行，填 `cloudrun/Dockerfile`，效果等价
3. 环境变量：`DATABASE_URL` = Supabase **Shared Pooler（Transaction mode, 6543）** 连接串。**不能用 `.env` 里的 5432 直连**，原因见下方。
   - 形态：`postgresql://postgres.[PROJECT-REF]:[PASSWORD]@aws-1-us-west-2.pooler.supabase.com:6543/postgres`
   - 注意主机名和用户名**都和直连不一样**：用户名要从 `postgres` 改成 `postgres.[PROJECT-REF]`，光把端口 5432 改成 6543 是连不上的
   - 最稳的取法是在 Supabase 控制台点 **Connect → Transaction pooler** 复制
   - 本项目实测可用节点：`aws-1-us-west-2.pooler.supabase.com`（aws-0 各 region 都是 `tenant not found`）
4. 环境变量改完必须**重新发布新版本**才注入容器。注意环境变量是**服务级**配置，不是版本级——同一个服务发布多少版都共享同一份，所以「换版本」解决不了环境变量问题。
5. 部署完成后，**服务设置 → 公网访问**先保持开启，用于验证；验证通过后可关闭，只留 `callContainer` 内网链路更安全。
6. 验证：

   ```bash
   curl https://<服务默认域名>/api/health   # 期望 {"status":"ok"}
   curl "https://<服务默认域名>/api/events" # 期望 events 数组非空
   ```

   本地不部署也能验证：`cd cloudrun && npm install && PORT=8787 node --env-file=../.env server.js`

## 7. 预览、上传、审核、发布

1. **真机预览**：开发者工具点「预览」，管理员/体验成员扫码。真机才走真实 `callContainer` 链路，模拟器不算数。
2. **上传**：点「上传」填版本号与备注，后台「版本管理」里出现体验版。
3. **类目**：个人主体别选「资讯」类目（个人不可选），建议 **工具 → 信息查询** 或 **生活服务**。功能与类目不符是最常见的驳回原因。
4. **用户隐私保护指引**（必填，最容易漏）：小程序后台「设置 → 服务内容声明 → 用户隐私保护指引」。必须如实声明收集的信息，否则直接驳回。本项目实际涉及：① `wx.cloud` 的 `traceUser`（会关联 openid，需声明"用户身份标识"）；② 收藏数据存在**本地 Storage**（未上传服务器，可不声明为收集）。图片/内容来自第三方源，不涉及用户上传。
5. **提交审核**：后台「版本管理 → 提交审核」，备好功能页面截图和类目。个人主体一般 1–3 天。
6. **发布**：审核通过后点「发布」。此后数据由 GitHub Actions 每两日更新，小程序无需重新发版。

> **节奏建议**：真机预览随时可用且**不需要审核**，可以先用它验收；但**提审材料要按最终形态准备**（功能截图、类目说明），UI 大改就要重做一遍，所以建议 UI 定稿后再提审。

## 8. 排障速查

| 现象 | 原因 |
| ---- | ---- |
| 发布时报 `代码仓库中没有找到Dockerfile` | 云托管只在**仓库根目录**找 Dockerfile，放子目录不认（或改用高级设置指定路径） |
| `/api/health` 返回 `unhealthy` | 绝大多数是两种情况之一：① `DATABASE_URL` **压根没配**（云托管的环境变量是**服务级**、不是版本级，反复换版本永远解决不了，去「服务设置 → 环境变量」加，保存后重新发布）；② 配的是 5432 直连串——Supabase 的 `db.[ref].supabase.co` 是 **IPv6-only**（只有 AAAA 记录、没有 A 记录），云托管容器是 IPv4 网络必然连不上，要用 Shared Pooler（6543）且用户名带 `.[PROJECT-REF]` 后缀 |
| 想知道容器里实际读到的连接参数是什么 | 临时加一个诊断端点回显 `process.env.DATABASE_URL` 的**形态**（host 前缀 / 端口 / 是否 shared pooler / 用户名是否带 ref 后缀）+ 真实连接错误原文，**不要回显密码**。这是定位这类问题最快的一招——比反复猜「是网络问题还是参数问题」高效得多。定位完记得删掉。附带技巧：响应耗时也是信号，**0.2–0.4s 的快速失败**说明是连接参数问题，不是网络不通（网络不通会卡几秒到几十秒） |
| 页面提示「请先在 config.js 中配置云托管环境 ID」 | `CLOUD_ENV` 为空 |
| `callContainer` 返回 404（页面提示「服务返回 404」） | 未必是容器返回的。**先看响应体里的 `code`**：<br>① `INVALID_HOST`（`Invalid host`，带 `requestId`）→ **是 CloudBase 网关返回的**。官方定义：「无效或者非法的主机名」——即 env 拼出来的 host 不是 CloudBase 合法地址。**排查顺序：先用「复制小程序示例」拿到权威 env ID 与服务名逐一比对**（界面上只有环境**名字**、没有 ID，极易抄错）；两者都对却仍报，则不是客户端参数问题，而是**调用的 AppID 不是该环境的归属方**（多账号 / 云托管开通在另一个小程序下）。签名特征：给 `wx.cloud.init()` 传该 env 会报 `-601034 没有权限，请先开通云托管`<br>② 看到 `served_by: shanghai-weekly-events cloudrun service` 的 JSON → 请求**已到达本容器**，纯属 path 没匹配（看回显的 `original_url`）<br>③ 服务名不存在类错误（`-601031 EnvDbId [], ServiceName [] not exist`）→ 服务名/环境 ID 写错，或第一个字是空的空服务 |
| `callContainer` 报 `-601034 没有权限，请先开通云托管` | AppID 未开通微信云托管，且未被同主体已开通的环境设置「资源复用」。到**微信云托管控制台用该小程序登录并开通**（不是在 mp 后台、也不是勾选「云开发」就能替代） |
| `callContainer` 报无权访问 | 云托管环境未与该 AppID 关联（换环境了 / 选错小程序） |
| 已确认 env / 服务名都正确，仍报 `INVALID_HOST` | 说明**环境本身不属于调用它的这个小程序**。核对方法：开发者工具 →「云开发」→ 环境详情，看「**所属应用**」是不是本项目的 AppID、「**环境 ID**」是不是你填的那个。注意同一个微信号可以管理多个小程序，所以"同一个微信号"不能排除此问题。修复：把云托管服务部署到**归属于本 AppID 的环境**（云托管控制台环境下拉里挑一个属于本小程序的），再同步改 `config.js` 的 `CLOUD_ENV`。`callContainer` **默认不支持跨环境**，跨主体还要靠「资源复用」 |
| 云托管「我的环境」里找不到自己的环境 | **小程序是在扫码登录云托管时选定的**（官方原文：「进入控制台之前，会提示要求你选择『小程序/公众号』」），环境归属跟着这个选择走。改用无痕窗口打开 `cloud.weixin.qq.com` 重新扫码，在「选择小程序/公众号」那一步选对 AppID。注意**选择列表按小程序名称展示**，不是 AppID，先进开发者工具「详情 → 基本信息」确认名称再选 |
| ⚠️ 别指望在云开发控制台里看到云托管环境 | 官方 FAQ：「微信云托管和微信云开发是**两套独立体系**，微信云托管的环境只能**在微信云托管控制台**看到，在开发者工具的云开发控制台中不能看到」。两者只共享**腾讯云账号**（内网联通需配相同 VPC）。所以"云托管列表里没有云开发那个环境"是**正常现象**，不能用来判断小程序选错了 |
| 首次进云托管被迫走「选择模板」向导 | 说明当前登录的小程序**名下还没有云托管环境**，会进入无门槛部署流程。快速入门有两条路：**无门槛部署**（模板）和**自定义部署**。若页面上有「自定义部署」入口，优先用它（可直接填环境名称 + 服务名称，服务名称填 `events-api`）；否则挑一个**最轻的模板**把环境建起来（多数模板会顺带开 MySQL，建议选没写 MySQL 的那个），**创建后把模板服务删掉**再新建自己的服务——官方明确：自动创建的服务「你可以部署使用，也可以删除」，服务名称不可修改 |
| ⚠️ 环境别随便删 | 官方规则：单个小程序最多 3 个环境，**仅第 1 个环境带 3 个月免费额度**；**删除环境后重建不再有免费额度**（额度不恢复）。所以环境建错/搬家时，先留着旧的跑通新的再说 |
| 列表一直「加载中」或 0 条 | `DATABASE_URL` 没填或填错，先 curl `/api/health` |
| 图片大面积裂图 | 相对路径 / 图床防盗链，见第 2 节 |
| 开发者工具正常、真机空白 | 真机用的是线上云托管服务，确认服务已发布版本且公网访问开启 |

| ⚠️ 别用云托管的「一键部署」向导建环境 | 该向导（`选择模板 → 服务部署 → 开始使用`，标题如「Express.js 一键部署」，字段是**环境名称**）会顺手装一个 Express 模板服务，并**自动开通数据库**，白占资源。我们要的是「**新建服务 → GitHub 仓库**」直接部署本仓库。另外：**微信云托管没有"选小程序"这一步**——小程序是在**首次进入云托管控制台时**选定的，之后会话固定，向导里不会再问 |
| 想知道「正确的 env ID 到底是多少」 | 云托管控制台服务详情 →「线上版本」卡片右侧有「**复制小程序示例**」按钮，它会生成一段官方 callContainer 样例，里面的 `config.env` 就是**该服务所在环境的权威 ID**。这是最可靠的来源——**别在界面上找**，控制台只显示环境**名字**（如「环境 prod」），不显示 ID，很容易抄到别的环境的 ID。注意 FAQ 明确：要填**环境 ID，不是环境名** |
| 怀疑「是不是 callContainer 缓存了上次的失败」 | 看两次请求的 `requestId`：若完全相同，说明第二次**没有真的发包**，是 SDK 返回的缓存失败结果。改完配置必须**重新编译**才能发起真实请求 |
| 调用链路已经打通到哪一层了？ | 错误码会逐层递进，可当进度条用：`-601034 没有权限，请先开通云托管`（权限层）→ `85088 system error`（云能力初始化）→ `INVALID_HOST`（网关地址解析层）。看到 `INVALID_HOST` 说明权限与初始化都过了，只剩「环境 ID + 服务名」这一对没对上 |

## 9. 已知边界

- 个人主体不能用 `web-view`，第三方报名页任何主体都无法内嵌，报名统一走复制链接（已实现）。
- 收藏存在本地 Storage，换设备不同步；需要跨设备时再上云托管用户态（`X-WX-OPENID` 由平台自动注入）。

## 9.1 数据保留与清理（2026-10-03 重构）

**展示口径与存储口径是两件事，不要混。**

| | 规则 | 代码位置 |
| --- | --- | --- |
| 展示（读） | 只出**未结束**的活动：`(coalesce(end_time, start_time) at time zone 'Asia/Shanghai')::date >= 今天的上海日期`，上界仍为今天 +14 天 | `src/lib/repository.js` 的 `buildEventWindowWhereSql`、`cloudrun/server.js` 的同名函数（**两处必须一致**） |
| 存储（清理） | 删除**结束时间**早于 7 天前的行 | `src/lib/repository.js` 的 `buildCleanupSql`，`EVENT_RETENTION_DAYS = 7` |

**两个必须知道的坑：**

1. **清理的判定基准必须是 `coalesce(end_time, start_time)`，不是 `start_time`。**
   长期展览（如 7 月开幕、次年才结束）的 `start_time` 很早，按 `start_time` 会被误删——但它仍在展出，是有效内容。实测：本库有 143 条"开始很早但还没结束"的活动，按旧写法会全部被误删。
2. **定时任务的 cron 字段顺序是「分 时 日 月 周」。**
   `cleanup.yml` 曾写成 `0 2 1 */2 *`，那个 `*/2` 落在**月**字段 → 等价于"奇数月 1 号"，一年只跑 6 次，导致过期数据堆了三个月。正确写法见 `collect.yml` 的 `0 1 */2 * *`（每 2 天）。现已改为每天 `0 3 * * *`。

另外：`raw_event_ids` / `sources` 这类 jsonb 大字段在**本地脚本里用 `select *` 拉取时可能让进程被系统杀掉**（实测 exit 137），备份脚本请显式列字段。

## 9.2 长期活动的 end_time 补齐与「发布/读窗口口径一致」铁律（2026-10-03）

### 问题一：长期活动没有 end_time，会同时坏掉展示和读窗口

展览、驻场演出的源页面经常只给开始日期。`end_time is null` 时，
`coalesce(end_time, start_time)` 会落到 `start_time` 上，于是这档活动被当成「开幕当天就结束」——
读窗口不显示它，清理任务也会在开幕 7 天后把它删掉。

**解法**：`src/lib/event-duration.js` 提供 `inferEventEndTime(event)`，
在发布收口 `filterPublishableEvents`（`src/lib/events.js`）里对每条事件生效：

| 判定 | 结果 |
| --- | --- |
| 源已给结束时间且晚于开始 | 原样保留（一手数据优先） |
| 命中单场信号（`音乐会/独奏/交响/协奏曲/室内乐/开幕/导览/讲座/沙龙/工作坊/放映…`） | **保持 null** |
| 类别是 `展览`，或命中长档期信号（`音乐剧/话剧/舞台剧/歌剧/沉浸式/驻场/驻演/公演/剧场/演出季/艺术节/市集…`） | `start_time + 90 天` |

**为什么必须「选择性」补齐**：给一场钢琴独奏编 3 个月结束时间，会让它在首页挂三个月并挤掉真正的活动——
那是把错误放大，不是修掉。单场信号优先级高于长档期信号。

存量行用 `node scripts/backfill-end-time.mjs`（默认干跑，`--apply` 才写，写入前自动落 JSON 备份到
`.workbuddy/backups/`）。幂等：只处理 `end_time is null` 的行。
2026-10-03 首次执行：370 行里 93 行 `end_time is null`，判定补 7 行、留 86 行，读窗口召回 276 → 277。

### 问题二：发布口径必须与读窗口口径完全一致

`publishEvents` → `replaceWeekEvents` 的实现是**「先按读窗口 `delete from events`，再插回本次采集集」**。
所以只要发布口径（`isInDateRange`）比读窗口口径（`buildEventWindowWhereSql`）**窄**，
落在两者差集里的行就会被**删掉且永远不再写回**。

旧实现里 `isInDateRange` 带着「展览回看 60 天 / 高校讲座回看 30 天」的分类分支，
而读窗口没有这个上界收缩 —— 实测：**读窗口 277 行里有 147 行**会被静默吃掉，
包括 `世界树之巅：美洲古代文明大展`（7.9 开幕）、`塑我此生：贾科梅蒂艺术大展`（7.17 开幕）等仍在展的长期展览。

现在两处统一为同一条判据：

```
start_time <= endDate 且 coalesce(end_time, start_time) >= startDate
```

`test/repository.test.js` 里有一条回归护栏专门钉这个不变量
（`publish predicate matches the read window so long-running events are never dropped`），**不要删**。

## 9.3 小程序排序：推荐 / 最新（2026-10-03）

小程序原来只有「按 start_time 升序」，Web 的评分体系没跟过来，两端首屏顺序不一致。
现已在 `miniprogram/utils/sort.js` 移植 Web 的 `scoreEvent`，首页加了「推荐 / 最新」分段控件。

| 档位 | 行为 |
| --- | --- |
| 推荐（默认） | 按评分降序。评分项：多源交叉验证 `min(源数,4)×8`、一手源 T1 `+12`、类别（演出音乐 14 / 展览 10 / 线下活动 6）、有报名链接 `+6`、有封面图 `+20`、周末 `+10`、18 点后 `+8`、临近度 `max(0, 14-天数×2)`、标题关键词（音乐节 18 / 开幕 16 / 限定 14…）、中文标题 `+28` |
| 最新 | 严格按 `start_time` 升序（展览档按「有封面优先」排） |

例外：**高校讲座两档都走 `sortCampusLectures`**（AI 相关置顶，其余近期在前、已发生排后），
与 Web 类目页行为一致——讲座的用户意图是「锁定最近一场」，不是「看推荐」。

⚠️ 评分规则改动必须**同步改 Web 端 `src/lib/recommendations.js` 的 `scoreEvent`**，否则两端首页顺序会漂。

另外：首页的**分类切换与排序切换都在本地重排**（接口一次返回 14 天全量），只有搜索走服务端。

## 9.4 日期区间展示（2026-10-03）

`miniprogram/utils/format.js` 提供两个格式化函数，分工不同：

| 函数 | 用途 | 跨月长期展的输出 |
| --- | --- | --- |
| `eventRangeShort` | 列表卡片（紧凑） | `9.24–10.30` |
| `eventPeriod` | 详情页（完整） | `9月24日 周四 10:00 至 10月30日 周五` |

两者在**跨日时都不带结束钟点**——跨的是"档期"，结束时刻是当天闭馆时间，没有信息量。
同一天的活动仍然保留钟点（`10.6 19:30–21:30`）。

卡片角标 `eventBadge`：今天/明天/后天优先；已开幕但未结束的长期活动标**「进行中」**
（这类活动的 `start_time` 在很久以前，`relativeLabel` 返回空，不加这层用户会以为它没有时间信息）。
